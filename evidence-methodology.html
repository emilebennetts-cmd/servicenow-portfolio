Evidence governance · November 2026

What the portfolio proves — and what it does not

Architecture diagrams, code repositories, screenshots and runtime demonstrations are different kinds of evidence. This guide makes their boundaries explicit so technical reviewers can assess each claim without assuming a production deployment.

Verification classifications

SOURCE-ONLY

Implementation files, configuration definitions, tests or documentation exist in a repository. This does not establish that the solution was installed, executed or accepted in an instance.

MOCK-ONLY

A conceptual diagram, static HTML demonstration or illustrative workflow communicates intended behaviour. It is not evidence of ServiceNow runtime behaviour.

DEV-VERIFIED

A named feature has been observed in an authorised development instance, with a dated test result and sufficient reproducible evidence. Verification is limited to the stated instance, build and scope.

PRODUCTION-VERIFIED

Functionality has been observed in an authorised production environment with appropriately approved, sanitised evidence. A successful development test never implies production verification.

Screenshot publication gate

Genuine images are not automatically safe to publish. Customer names, request data, email addresses, tenant identifiers, URLs, internal topology and hidden metadata must be reviewed before any public gallery entry is released.

  1. Record provenance, capture date, environment and the specific feature being demonstrated.
  2. Create a separate, irreversibly redacted derivative; retain originals only in an authorised private location.
  3. Remove metadata and inspect the final rendered image at full resolution.
  4. Record SHA-256 of the exact derivative and an explicit approval decision.
  5. Publish only an approved derivative in the designated public screenshot directory; reject changed files until reapproved.
  6. Validate image loading, captions, mobile rendering and evidence classification after deployment.

Current boundary: This page does not certify or release any screenshots. An absent gallery is preferable to unreviewed customer evidence.

Architectural assurance

These Workbench case studies describe an OOTB-first approach aligned with ITIL 4 practices: traceable requirements, least-privilege access, controlled change, reusable delivery patterns and human approval for consequential remediation. A documented design is not a claim that every described integration is operational.

Licensing: This static website needs no ServiceNow entitlement. Runtime custom applications may require App Engine entitlements. ITSM, ITOM, IntegrationHub, Performance Analytics, AI capabilities and external integrations must be assessed against the customer's subscriptions and contract.
