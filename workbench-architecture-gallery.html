What a technical reviewer can inspect

Open each evidence path to distinguish implementation artefacts from runtime claims. This is a review checklist, not an assertion that every feature was tested.

Diagnostic / source inspection
  • Inspect scoped application structure and documented collection boundaries in the Diagnostic repository.
  • Check read-only assessment assumptions, access controls, and the human review stage.
  • Request a dated instance test record before treating a finding as DEV-verified.

Review public Diagnostic evidence summary →

Delivery / reusable patterns
  • Trace a requirement to a reusable pattern, implementation task and acceptance criterion.
  • Check whether the artefact is a source template, a synthetic walkthrough or an actual instance result.
  • Verify the version and instance identity for any historical DEV read-back.

Review public Delivery evidence summary →

Release / evidence promotion
  • Require a versioned change record, test outcome and approval before promoting an environment claim.
  • Do not infer production acceptance from a GitHub commit or a successful website deployment.
  • Record failed tests and limitations alongside successful checks.

Evidence verification method

Screenshots / publication decision
  • Confirm image origin, instance, date, ownership and permission to publish.
  • Remove customer names, identifiers, instance URLs, tokens and metadata irreversibly.
  • Keep unapproved source captures out of public Git history, even when blurred previews look safe.

Publication gate

Website quality evidence: Static-site commits, CI test runs and GitHub Pages deployment have their own release records. A successful browser or publication gate verifies only the portfolio website, not ServiceNow native execution. Inspect the public quality approach and the unrun native acceptance matrix.

Architecture and entitlements

Prefer OOTB capabilities, scoped application boundaries, least-privilege roles, supported APIs, and ITIL 4-aligned change controls. This static website requires no ServiceNow licence. Runtime deployment may require App Engine/custom application entitlements, ITSM or ITOM subscriptions, IntegrationHub transactions/spokes, Performance Analytics, AI capabilities and third-party subscriptions. Validate requirements against the actual contract and implementation scope.
