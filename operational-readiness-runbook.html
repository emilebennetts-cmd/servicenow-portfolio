01 / The client's pain & history

The handover gap after a successful build

Delivery teams can hand over working-looking screens while support teams still lack named owners, alert thresholds, credential rotation, evidence retention and a tested restore route. The Workbench's controlled architecture and As-Built identify those controls as unresolved acceptance work, rather than assuming that documentation or an SDK build closes them.

Version-specific evidence: The controlled 30 September 2026 documents describe release 4.6.1 in source and historical 4.5.1 DEV read-back. These are different baselines. No subsequent release is claimed installed here, and no production verification is established.
Prevent silent bypass

Explicit gates and waivers

Unresolved scope, deployment preview problems and self-approval must remain visible, with an accountable owner.

Contain client-side risk

Consent and access boundaries

Bounded reads, least privilege, credential aliases and kill switches prevent unapproved convenience workarounds.

Make operations measurable

Named evidence and cadence

Daily, weekly, per-release and quarterly reviews produce reviewable action and incident records rather than unowned dashboards.

02 / The ServiceNow solution

Operational control catalogue

These source-derived checks map the As-Built support cadence and user guide to tangible records. Filter by cadence or search for an operational condition; this browser tool does not connect to a ServiceNow instance.

OPS-01 / DAILY

Failed scheduled jobs

Review failed executions and high-severity defects. Assign an incident or corrective owner before recurring failures compound.

Expected evidence: job execution outcome, affected engagement, remediation owner and linked incident where applicable.
OPS-02 / DAILY

Consent and scanner controls

Identify expired consent and read-only endpoint errors. Keep the scan disabled until authority and bounded configuration are restored.

Expected evidence: consent decision, scan error record and approved credential/endpoint review.
OPS-03 / DAILY

Integration and deployment drift

Review failures, drift signals and deferred-scope violations. Do not treat zero findings as proof that a disabled collector ran.

Expected evidence: failure classification, last successful run and assigned action.
OPS-04 / WEEKLY

Approval and waiver backlog

Review outstanding approvals, expired waivers and overdue decisions. Never let an expired exception silently close a gate.

Expected evidence: approval queue snapshot, waiver review and owner decision.
OPS-05 / WEEKLY

Artefact and scope freshness

Check stale outputs, estimate warnings, uplift clustering, upgrade rescoring and orphaned work links.

Expected evidence: reviewed report, scope reconciliation and prioritised remediation records.
OPS-06 / PER RELEASE

Pin source and package

Capture the approved source commit, package hash, changes and platform target before preview. Do not promote an unpinned artefact.

Expected evidence: release identity, source SHA, package hash and approver.
OPS-07 / PER RELEASE

Preview, remediate, re-preview

Resolve update-set collisions and missing dependencies; an unexplained preview failure is a hard stop, not a warning to skip.

Expected evidence: clean preview result and documented resolution of every problem.
OPS-08 / PER RELEASE

Independent runtime read-back

After authorised installation, inspect app version, counts, roles, privileges and smoke tests in that exact target environment.

Expected evidence: read-back receipt, negative ACL test and rollback rehearsal.
OPS-09 / QUARTERLY

Role and membership review

Check privileged, commercial, deployment, scanner and AI roles, plus membership and access revocation.

Expected evidence: least-privilege access review and named owner sign-off.
OPS-10 / QUARTERLY

Credentials and properties

Review credential rotation, integration aliases, safety switches and environment-specific properties.

Expected evidence: redacted credential inventory, rotation check and approved configuration baseline.
OPS-11 / QUARTERLY

Privacy and retention

Revalidate consent, data minimisation, retention and disposal authority before operational sign-off.

Expected evidence: approved privacy/retention decision and remediation tracking.
OPS-12 / QUARTERLY

Support and continuity readiness

Review support coverage, recovery commitments and restore rehearsal evidence; leave unsupported targets marked TBC.

Expected evidence: RTO/RPO decision, restore test and accountable service owner.

03 / Architectural best practices

Handover is an acceptance contract

ServiceNow OOTB capabilities—ACLs, update-set previews, application logs, platform notifications, incidents, changes, and scheduled executions—should be used before building bespoke orchestration. The controlled As-Built treats the following as unresolved until appropriate authorities sign off.

GateCurrent documented boundaryClosure evidence
Build and documentationSource package and controlled draft documentation preparedExact source reproduction and owner review
Release-specific DEV installHistorical 4.5.1 DEV read-back; 4.6.1 source only at documented cutoffAuthorised target preview, install, counts and roles read-back
Security and privacyDesigned controls; formal acceptance not demonstratedNegative ACL/UAT tests, threat and privacy approvals
Operational ownershipNamed business, technical and support signatories unresolvedRACI, monitoring, escalation, retention and on-call ownership
Recovery and performanceNo application-specific recovery rehearsal or capacity result in controlled baselineMeasured performance, approved RTO/RPO and restore test
Production promotionNot authorised or established by source reviewApproved change, rollback, smoke tests and operational acceptance
