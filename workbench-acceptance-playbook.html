Workbench acceptance playbook

How an architect would establish that a Workbench build is installed, configured and working — without confusing source artefacts, historical DEV records and actual runtime acceptance.

Verification levels

01 · Source inspection

SOURCE-ONLY

Review repository commit, manifest, scope, dependencies, tests and deployment instructions. This proves the presence of artefacts, not working behaviour.

02 · DEV read-back

DEV-VERIFIED only with receipts

Record instance, release, app version, scope, installation timestamp, role and a dated result for each executed test.

03 · Demonstration

MOCK-ONLY unless executed

Conceptual diagrams and synthetic walkthroughs communicate intended design; they do not satisfy acceptance tests.

04 · Production assurance

NOT ESTABLISHED

Requires authorised production change, monitoring and sign-off evidence; no such claim is made here.

Acceptance scenarios and expected evidence

A01 · Installation and scope integrity
  1. Read back application name, sys_scope identifier, version and installed dependencies from the target instance.
  2. Confirm application tables, roles, modules, ACLs and UI routes exist and are active where intended.
  3. Compare the installed build to the tagged source and approved update set or SDK deployment receipt.
  4. Capture redacted instance read-back, commit SHA, tester, timestamp and deviations.

Pass: identifiers and dependencies match the approved baseline; no unintended scope or privilege changes.

A02 · Diagnostic read-only collection and lineage
  1. Use a least-privilege test role and a known non-sensitive fixture set.
  2. Execute an approved read-only collector; record target table, filters, sample size and duration.
  3. Trace one finding back to collector version, rule, evidence reference and timestamp.
  4. Confirm the collector creates no customer configuration changes and handles denied ACL access without escalation.

Pass: attributable evidence and deterministic findings, with no unauthorised writes. Companion Knowledge Intelligence modules require separate navigation and deployment verification.

A03 · Delivery pattern selection and draft reconciliation
  1. Create a synthetic engagement and select a supported scope/module.
  2. Generate linked workshop questions, requirements, decisions, build guidance, unrun tests and handover actions.
  3. Edit an answer, rerun reconciliation and verify no duplicate records or overwritten approvals.
  4. Inspect pattern version, source reference and review-required fallback for unsupported scope types.

Pass: repeatable generation with preserved human decisions, traceable source and explicit review gates.

A04 · Approvals, roles and release assurance
  1. Exercise consultant, reviewer and unauthorised user roles against representative records and actions.
  2. Attempt release with an unmet acceptance gate; verify it remains blocked.
  3. Attach test results, decision record and handover checklist; confirm audit trail and reviewer identity.
  4. Validate upgrade-safe configuration and rollback against the approved non-production baseline.

Pass: least privilege, enforced gates, preserved traceability and reproducible rollback.

A05 · Optional integrations and failure handling
  1. Keep external writes disabled until an approved provider connection, mapping and entitlement are available.
  2. With synthetic data, test correlation IDs, replay/idempotency, timeouts, conflicts and retry behaviour.
  3. Prove inbound-authority rules do not overwrite approved ServiceNow decisions.
  4. Capture provider logs and redacted transaction IDs only after authorised end-to-end testing.

Pass: verified bidirectional behaviour only where specifically tested; otherwise label MOCK-ONLY or SOURCE-ONLY.

A06 · Mobile UX and accessibility
  1. Test at narrow viewport widths with no horizontal clipping, hidden controls or unusable tap targets.
  2. Navigate using keyboard alone; verify visible focus, skip links, headings and accessible labels.
  3. Confirm reduced-motion behaviour and legible contrast for evidence status labels.
  4. Retain browser, viewport, date and tester evidence.

Pass: critical tasks work on mobile and keyboard without inaccessible interactions.

Minimum acceptance receipt

For every test record: test_id · build_sha · app_version · instance_environment · scope · tester · execution_time · role · expected · actual · result · evidence_reference · defect_id · approver. Use non-sensitive synthetic data in public examples; keep raw instance receipts private until reviewed.

Evidence promotion rule: a test can be labelled DEV-VERIFIED only for the exact version and environment executed. A newer repository version resets the unverified delta. A screenshot without origin, permission and sanitisation is not publishable.

Source boundaries

Delivery source currently describes version 4.22.2; historical DEV evidence refers to an earlier baseline and must not be carried forward automatically. Diagnostic Workbench 2 documents its SDK application and a separately deployed Knowledge Intelligence companion package. These are source statements, not fresh instance verification.

The original Delivery and Diagnostic repositories are access-restricted, not public reviewer links. See the published Delivery case study, Diagnostic case study and evidence ledger for public-safe summaries. No private source files, private control materials or customer screenshots are embedded here.

Licensing and entitlement gates

The static portfolio requires no ServiceNow licence. A deployed custom Workbench may require App Engine/custom application entitlements and appropriate roles. ITSM, ITOM/Discovery, IntegrationHub spokes, Performance Analytics, Now Assist/AI and third-party provider subscriptions depend on actual enabled functionality and contractual rights; confirm with the platform owner before enabling integrations.
