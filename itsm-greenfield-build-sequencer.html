01 / The client's pain & history

Greenfield without an agreed baseline becomes brownfield by accident.

DISCOVERY

Workshops without decisions

Process questions are documented in isolation. No one confirms which native behaviour should be adopted, which change is justified or who signs off the requirements.

BUILD

Configuration before dependencies

Routing, catalogues, knowledge, approvals and reporting are built ahead of user/group governance and data ownership, producing avoidable rework and ACL surprises.

RELEASE

Test design mistaken for evidence

Draft tests are counted as passes, update sets are treated as proof of installed state and handover documentation arrives after production promotion.

These are representative delivery risks, not measured outcomes or allegations about any named customer.

What would promote this to DEV-VERIFIED?
Identify the target DEV instance, product release, installed plugin/versions, roles and build identity. Execute positive and negative cases for each agreed module; retain dated expected/observed results, supporting screenshots cleared for handling, defects and approver. An old or source-reported DEV statement does not verify new commits.


What would promote this to PRODUCTION-VERIFIED?
Separate authorised production change and deployment records, rollback outcome, production configuration read-back and business/service-owner acceptance. Neither this page nor repository code establishes that evidence.


Licensing and entitlements
The static browser demonstration needs no ServiceNow licence. A real implementation requires contractual confirmation of core ITSM rights, licensed capabilities (including any ITSM Pro/Enterprise features), user roles and custom application/App Engine limits. Discovery/ITOM Visibility, CMDB-related connectors, IntegrationHub spokes and transaction allowances, Performance Analytics, AI and provider subscriptions may require separate entitlements. Feature availability is release- and contract-dependent.
