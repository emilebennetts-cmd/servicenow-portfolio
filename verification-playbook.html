Independent verification · Not a certification

How to turn source evidence into verified application evidence.

This playbook describes the evidence required to advance a capability from SOURCE-ONLY or MOCK-ONLY to independently DEV-VERIFIED. No new runtime verification is claimed by this page.

1. The client's pain & history

Application source, deployment notes and polished demos are often mistaken for executed acceptance evidence. This creates risk when evaluating a platform implementation, particularly when multiple application scopes and DEV baselines exist.

2. The ServiceNow solution

01 · Identify target

Record instance, date, authenticated persona, application sys_id, technical scope, version and deployment package. Do not substitute original PDI identities for demo7 identities.

02 · Establish baseline

Confirm installed application metadata, required tables, ACLs, roles, dependencies and licensing. Capture read-only evidence before test execution.

03 · Exercise Diagnostic

Use synthetic records to test collector permissions, read-only boundaries, findings provenance and governed Knowledge Intelligence. Record failures and remediation.

04 · Exercise Delivery

Test scope selection, pattern preview, generate/reconcile idempotency, preservation of edits, decisions, unrun tests, document generation and approval gates.

05 · Test handoff

Verify that Delivery references Diagnostic findings without acquiring writable ownership of operational evidence. Check deep links and role restrictions.

06 · Capture evidence

For each case retain test ID, preconditions, steps, expected and actual result, timestamp, reviewer, build identity and sanitized capture reference.

3. Architectural best practices

Prefer OOTB configuration and least-privilege personas. Separate functional acceptance from deployment, integration and security assurance. Retain failing tests in the register rather than presenting them as successful. No screenshot should be published until its origin, ownership and confidentiality have been reviewed.

Classification rules:

SOURCE-ONLY means code or documentation exists. MOCK-ONLY means illustrative or simulated behaviour. DEV-VERIFIED requires independently observed execution in an identified authorised DEV environment. PRODUCTION-VERIFIED requires separately authorised production evidence. CI success validates the website pipeline, not ServiceNow runtime.

Acceptance artefacts

Use the acceptance matrix, technical walkthrough and website CI evidence as separate evidence sources. Record blocked cases explicitly; never infer passing results from source or demos.

Licensing and entitlements

This static playbook requires no ServiceNow licence. Executing tests requires authorised DEV access, appropriate custom application rights and test personas. ITSM, ITOM, IntegrationHub, Performance Analytics, AI features and third-party integration connectors may require separate entitlements, depending on the tested capability.
