01 / The client's pain & history

Too many CIs, too little trust in the evidence

A representative enterprise may operate multiple discovery sources, stale servers, contested CI ownership, inconsistent identifiers and duplicate relationships. An exported count appears authoritative until the denominator is missing, a query is incompatible with the release, or a grouping cap silently truncates the result. This is a representative scenario, not a claim of a named customer engagement or verified customer outcome.

Identity

Duplicates and collisions

CI names and hardware identifiers can converge across discovery feeds. A count of name matches is not, by itself, an IRE collision finding.

Governance

Unowned or stale records

Age, ownership and lifecycle indicators need class-aware thresholds before triage. A missing value must not be silently treated as healthy.

Relationships

Weak topology evidence

Missing parent/child references and relationship-type distribution are diagnostic signals, not proof that every service dependency is correctly mapped.

03 / Architectural best practices

Source review surfaced four important evidence risks

01 · Aggregate-only does not automatically mean disclosure-safe

The source declares a read-only/PII-free posture, yet some grouped result records can include display values of CI names and hardware serial numbers. Those values may be internal asset identifiers. Control: redact or suppress group labels before export, enforce a disclosure allowlist, and review the resulting evidence envelope before it leaves the approved environment. A source metadata flag is not a privacy audit.

02 · Group limits can undercount duplicate populations

Source-defined grouping stops after a finite number of distinct groups. Duplicate-cluster totals calculated from that partial set can be incomplete; this is not merely a visual top-N cap. Control: emit an explicit truncated/partial status, track scanned groups and avoid reporting an unqualified duplicate ratio as complete. Validate query performance at realistic CMDB scale.

03 · Unavailable tables and null results require three-state handling

Some counts use a sentinel when a table is absent, while certain derived metrics can fall back to zero or empty arrays. Absence of evidence must not become a healthy score. Control: distinguish PASS, FAIL and NOT ASSESSED / PARTIAL; expose table/field availability and confidence alongside every result.

04 · A relationship total can double-count and still miss topology defects

Summing missing-parent and missing-child counts can count a row twice when both references are empty. The current reviewed relationship aggregation does not establish duplicate-edge or self-reference findings despite broader module descriptions. Control: deduplicate the union, test boundary cases, then add explicit typed-relationship and referential-integrity checks as separate requirements.

Safety boundary:

Read-only describes mutation behaviour, not authorisation, scalability, quality or export safety. Any collector should be executed only with approved access, on an authorised instance, using release-validated queries and an agreed evidence retention policy. 04 / Definition of done

What would make the CMDB assessment genuinely verified?

ATF / test data

Positive and negative fixture coverage

Verify one valid identifier, an intentional duplicate, missing name/owner, both-null relationship and retired-operational server. Confirm the expected count and status for each.

Failure behaviour

Unsupported release conditions

Simulate an unavailable table/field, invalid encoded query and timeout; assert NOT ASSESSED or PARTIAL with a cause, never a zero interpreted as healthy.

Security

Approved export

Prove no disallowed CI names, serials, user fields, secret values, instance URLs or customer branding escape through evidence records, logs and screenshots.

Scale

Measured performance

Record class size, group cardinality, duration, caps and query plan in DEV with representative volumes. Prove no omitted groups are silently reported as complete.

Platform OOTB

IRE and CMDB Health reconciliation

Compare findings with Identification and Reconciliation Engine configuration, CI Class Manager, CMDB Health and applicable CSDM guidance; record explained discrepancies.

Release receipt

Evidence attached to version

Record source SHA, collector version, instance/release, tester, execution time, expected/actual outcome, ACL approval and sign-off before claiming DEV-VERIFIED.

Current evidence: SOURCE-ONLY technical review of implementation files. Technical approach

Upgrade-safe, OOTB-first

Use the platform's standard CMDB Health, IRE rules, CI Class Manager and CSDM relationships as the system of record. Treat custom read-only diagnostics as supporting evidence with transparent limits; do not duplicate reconciliation logic or update CI records through an assessment collector. Govern fixes through normal change, test and promotion controls.
