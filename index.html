01 / Diagnostic engineering

From unstructured script output to traceable findings

Problem: Ad hoc diagnostic output is difficult to validate and compare across assessments.

Mechanism: Read-only module collectors emit a defined evidence envelope; intake validation rejects unsafe or malformed submissions before rules and correlations create reviewable draft findings.

Inspect implementation and evidence boundary

Source: Diagnostic Workbench 2 build documentation describes the envelope markers, validation ledger, 42 rules and four correlations. Counts are repository-reported, not live runtime measurements.

To verify: Run a synthetic envelope through intake in an authorised DEV instance and retain redacted validation and finding outputs.

02 / Delivery engineering

From repeated discovery to governed implementation

Problem: Starting each engagement from blank workshops, requirements and design documents increases rework and inconsistency.

Mechanism: Scope-specific implementation presets propose linked workshop questions, requirements, build guidance, unrun tests and handover actions while preserving edited answers and approval gates.

Inspect implementation and evidence boundary

Source: Universal Delivery Workbench implementation-preset release documentation and repository README. Reuse is governed; candidate patterns are not automatically approved.

03 / Architecture and controls

From diagnostic observations to an accountable delivery decision

Problem: Operational findings lose provenance when copied into delivery work.

Mechanism: Diagnostic retains writable operational evidence; Delivery carries source references and reviewed handoffs rather than maintaining a second writable evidence store.

Inspect implementation and evidence boundary

Source: Delivery Workbench architecture and repository README describe the ownership boundary. The public cross-workbench walkthrough is illustrative.

To verify: Demonstrate an authorised end-to-end handoff, record source-reference integrity and verify that no duplicate writable evidence is created.

How the diagnostic engine actually works

Evidence processing pipeline

Read-only collector→DIAG envelope→Validation ledger→Rules and correlations→Draft findings→Human review→Assessment and export
1. Collection and data boundary

Collectors are read-only and aggregate-only. The Workbench does not execute scripts against the instance. Operators run authorised scripts separately, then paste or upload text, log or JSON results. The common DIAG envelope marks the submitted evidence boundary.

2. Evidence validation

Evidence intake checks declared read-only status, refuses consumer-level data and scans for secrets before acceptance. Rejected input must not enter the findings pipeline. The validation ledger preserves the distinction between received and accepted evidence.

3. Findings, severity and confidence

Configured rules and cross-module correlations classify accepted evidence into Critical, High, Medium and Low findings. Proposed solutions remain DRAFT until reviewed. Module packs without accepted evidence show “Not assessed” rather than a misleading healthy score.

4. Reports and delivery handoff

Accepted findings feed an assessment summary, issue and artefact explorer and delivery package. A handoff to a separate delivery application is a reference/design boundary, not proof of a live synchronised integration.

5. What has actually been tested?

The repository reports a 1 September 2026 local Playwright run across 19 views, with zero console errors, plus historical DEV acceptance of paste → validate → findings → pack health. This is historical DEV-reported evidence; this portfolio has not independently repeated those tests or verified production use.
