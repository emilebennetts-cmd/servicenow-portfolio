01 / The client's pain & history

In a typical mature ServiceNow estate, consultants inherit inconsistent configuration documentation, uncertain data quality and scattered operational evidence. Unreviewed diagnostic scripts can add risk, while findings without traceable source metrics are difficult to defend. This is a representative consulting problem, not a measured claim about a named customer.

02 / The ServiceNow solution

The access-restricted Diagnostic Workbench 2 source documents a scoped application and a separately deployed Knowledge Intelligence companion. Its documented chain connects governed knowledge sources, symptoms and discovery questions to read-only collectors, evidence records, rules, findings awaiting review and solution patterns.

02a / Technical implementation: two distinct runtime lanes

The source baseline deliberately separates the local-first Diagnostic Workbench UI from the Knowledge Intelligence companion package. They share an assessment purpose but must not be presented as an automatically integrated, production-proven pipeline.

CORE WORKBENCH · SOURCE-ONLY

Assessment and guided diagnosis

The documented UI uses a ServiceNow page and compressed browser bundle with an IndexedDB local-first working store.

  • 18-stage, six-phase assessment model, guided runbooks and script library.
  • Operator-supplied read-only evidence envelopes; validation rejects declared consumer data and scans for secrets.
  • Rule-derived draft findings, pack health, report/export and delivery package.
  • Does not run collectors or retain instance credentials in the browser.
KNOWLEDGE INTELLIGENCE · SEPARATE PACKAGE

Governed knowledge-to-finding records

The companion package documents 16 scoped tables, specific roles and ACLs, a seed importer, rule evaluation and evidence-linked draft findings.

  • 16 knowledge packs, 45 read-only collectors, 65 rules and 38 solution patterns in the source seed inventory.
  • Collector lint rejects mutating operations; a human must approve findings before client publication.
  • Knowledge content starts empty; article import requires lawful reuse rights.
  • The companion's Classic modules are not yet wired into local-first Workbench page navigation.

Boundary that matters: The source workflow has an authorised consultant execute a collector separately in an approved non-production instance, then paste the evidence into the appropriate intake. This page does not claim that the Workbench executes scripts, that the two stores are automatically synchronised, or that a customer implementation is production-ready. The two stores are not automatically synchronised.

CORE WORKBENCH · DW-01

Define the assessment boundary

Select an approved sub-production target and document the symptoms, scope exclusions, owner and collection constraints.

Expected evidence: Signed scope, assessment version and agreed objective.

Stop/go boundary: No customer-instance activity without explicit authority.

CORE WORKBENCH · DW-02

Choose guided diagnosis

Use the documented guided runbook and module-pack catalogue to select evidence-first checks for the stated symptom.

Expected evidence: Question-to-collector map with module and runbook references.

Stop/go boundary: Catalogue membership is not evidence that a customer fault exists.

CORE WORKBENCH · DW-03

Approve read-only collection

Inspect the collector for aggregate-only behaviour, target permissions, bounded execution and an authorised operator.

Expected evidence: Collector review, consent, instance scope and operator authorisation.

Stop/go boundary: Never launch collection from this website; source says scripts run separately.

CORE WORKBENCH · DW-04

Validate the DIAG evidence envelope

Paste only minimised collector output into the controlled Workbench intake and inspect validation, secret checks and rejected payloads.

Expected evidence: Marked read-only envelope, acceptance/rejection result, source and run timestamp.

Stop/go boundary: Reject consumer data and secrets; ingestion is not remediation.

CORE WORKBENCH · DW-05

Examine rule and correlation findings

Check evidence/metric references for the documented rule and correlation outputs; inspect draft solutions.

Expected evidence: Rule identity, metric provenance, confidence limitations and DRAFT disposition.

Stop/go boundary: Correlation is not causation; draft findings are not confirmed defects.

CORE WORKBENCH · DW-06

Review pack health and unassessed areas

Compare assessed module packs with missing envelopes and explicitly record unassessed coverage.

Expected evidence: Pack coverage snapshot and list of gaps marked Not assessed.

Stop/go boundary: Missing evidence must never produce a healthy score.

CORE WORKBENCH · DW-07

Independently review a finding

Review evidence quality, impact, risk and solution applicability before any approved client recommendation.

Expected evidence: Dated review decision, author and approver separation, justified disposition.

Stop/go boundary: Neither scripts nor rule results may self-approve a finding.

CORE WORKBENCH · DW-08

Prepare controlled report and handover

Reconcile the findings register, known gaps and delivery package, then route the result through the receiving team's governance.

Expected evidence: Versioned assessment, approved recipient and risk/decision links.

Stop/go boundary: A generated export is not target deployment or cross-Workbench integration.

KI COMPANION · KI-01

Check Knowledge Intelligence packaging and rights

Treat KI 0.1.0 as a separately deployed companion; check scoped roles, ACLs, source licences and preview controls.

Expected evidence: Target scope record, approved content rights, update-set preview and persona-negative ACL plan.

Stop/go boundary: Source inventory is not an installed baseline; Classic KI pages are not linked to the local-first UI.

KI COMPANION · KI-02

Review KI evidence-to-rule chain

Use authorised KI collector execution, evidence markers and review-pending findings; require a human before publishing a pattern recommendation.

Expected evidence: Collector lint/authorised execution receipt, evidence-to-metric-to-rule links and independent reviewer.

Stop/go boundary: Historic 30 September 2026 DEV report is not a new DEV-VERIFIED test.

Licensing: this website needs none. Actual app/companion installation is subject to ServiceNow custom application / App Engine entitlements, role/ACL assignment, non-production access, update-set controls and the contracted ITSM/ITOM capabilities. 03 / Architectural best practices

Prefer OOTB reporting and supported read APIs where practical; constrain scoped app roles and ACLs, keep client data within approved boundaries, review script permissions and retain reproducible evidence. A read-only design does not itself establish that running scripts is authorised. Follow ITIL 4 continual improvement principles, segregate DEV from production verification and version deployment artefacts through controlled change.
